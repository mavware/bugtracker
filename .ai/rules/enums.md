# Enums

## Roles and permissions: users.role drives every role-based gate — supersedes the is_admin / EnsureUserIsAdmin note
CORRECTION to the middleware rule: users.is_admin and app/Http/Middleware/EnsureUserIsAdmin (the 'admin' alias) are gone since 2026-09-15. An account has one users.role (UserRole enum: homeowner default, professional, admin). What a role may do is derived in UserRole::permissions(), never stored: Permission::AccessAdmin (the /admin panel) and Permission::ManageCustomers (the customers page; professional AND admin). AppServiceProvider registers one Gate per Permission case, so routes use `can:access-admin` / `can:manage-customers` and templates `@can(Permission::X->value)`; add a new permission by adding a case and mapping it, not by adding middleware. role is deliberately not #[Fillable] (User sets a default of homeowner in $attributes); it changes only via the admin users page (setRole, an admin cannot change their own), `php artisan user:promote {email} [--role=admin|professional] [--demote]`, or registration, which accepts only UserRole::selfAssignable() (never admin). Downstream customer pickers (⚡sessions, ⚡trends, ⚡night-details, claim-nights) are still keyed on whether the user has customers, not on the role, so a demoted professional keeps seeing their existing groupings. Do not add a Gate::before for admins: SurveillanceSessionPolicy stays owner-only because the frames are photos of someone's home.

## An account holds many roles (users.roles JSON) — supersedes the "one users.role" note
CORRECTION to "users.role drives every role-based gate": since 2026-09-15 (same day, before commit) users.roles is a JSON list cast with AsEnumCollection::of(UserRole::class); the single role column never shipped. User::hasPermission() is true when ANY held role grants it (UserRole::permissions() is unchanged, so Admin still carries ManageCustomers on its own). Use hasRole()/isAdmin() to ask about a role and whereJsonContains('roles', UserRole::X->value) to query one. roles is not #[Fillable]; change it only through grantRole()/revokeRole()/setRoles() (which dedupe and keep enum order), i.e. the admin users page toggleRole (an admin cannot touch their own roles, so the last admin can never lock everyone out), `php artisan user:promote {email} [--role=…] [--demote]` (grants or revokes ONE role, leaving the rest), or registration, which sets exactly one self-assignable role. An account may legitimately hold no role at all (every gate false; it can still record its own nights). Factory: withRoles([...]), admin(), professional() each set the list exactly.

## An admin may change their own roles except Admin itself
CORRECTION (2026-09-15) to "an admin cannot touch their own roles": on pages::admin.users an admin CAN grant or revoke their own Homeowner/Professional roles, both from the row checkboxes (toggleRole) and the edit dialog; only their own Admin role is locked (toggleRole 403s on it, the dialog's save() drops Admin from the submitted list and re-adds it when held, and both Admin checkboxes render disabled for the signed-in admin). The reason is unchanged: the last admin must never be able to lock everyone out. `php artisan user:promote --demote` is unaffected.
