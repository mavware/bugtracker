# Surveillance

## Surveillance ingestion: closed tracks only, idempotent inserts
The capture page's JS does all computer vision; the server only accepts closed tracks (never appends). Each track POST is an idempotent insert keyed by (surveillance_session_id, client_track_id) — retries and duplicates are safe by design, so never add append/merge semantics. Points are a JSON array on bug_tracks capped at 5000/track; verification crops ride inline as base64 JPEG (≤20KB decoded, magic-byte checked). Reference photos and crops live on the private local disk under surveillance/{session_id}/ and are served only via policy-checked ImageController routes — never the public disk.

## Session image responses are no-store — the URLs are id-keyed, not content-keyed
ImageController serves the reference frame and crops with 'Cache-Control: private, no-store' (ImageController::CACHE_HEADERS). Do not put a max-age back on these. The routes are /surveillance/{session}/reference-image and /surveillance/{session}/tracks/{track}/crop/{position} — keyed by id, so the same URL serves a different photo once a session is deleted and the id is handed out again (a reset dev database restarts at 1). With the old 'private, max-age=86400' the browser reused the previous session's photo for 24 hours without revalidating, which read as "deleting the session did not delete the picture". no-store also keeps photographs of the inside of a home out of the browser's on-disk cache, matching the owner-only policy.

## Importing a device-local night is idempotent per (user, imported_local_id) and never creates an Active session
POST surveillance/import (ImportController → ImportLocalNight) brings in a night a guest recorded in their browser. The browser sends it in chunks of ≤50 tracks; every chunk carries the night metadata plus the browser's uuid as local_id, and the first chunk carries reference_image as base64. firstOrCreate on (user_id, imported_local_id) — unique index — means any chunk can be retried or re-sent; StoreClosedTracks (shared with the live tracks endpoint) reports re-sent tracks as duplicates. The session is created already Completed/Aborted with started_at/ended_at from the payload and the name from SurveillanceSession::nightDateFor(started_at). Do NOT route claims through the live reference/tracks/end endpoints: storeReference stamps started_at = now() (wrong night date for trends) and a half-imported night would show as "recording now" on the tonight panel. The watch pages (WatchController, routes watch.capture / watch.report) are the only unauthenticated surveillance routes and touch no rows; keep them outside the auth group. The verified middleware is a no-op here — User does not implement MustVerifyEmail — so do not write tests asserting 403 for unverified users.

## planned_end_at is the device's deadline, reported once with the reference frame — the server never acts on it
surveillance_sessions.planned_end_at (nullable timestamp) arrives as an optional ISO `planned_end_at` field on the reference upload (buildReferenceForm sends it only when the night has a deadline; the local sink accepts and ignores it — both sinks share the storeReference input shape in index.d.ts). The capture device owns the deadline: capture.js checks it every second and calls the normal end flow. The server only displays it — the tonight card shows "ends HH:MM" and, when the session is still Active past it, an "overdue" callout in place of the stale-heartbeat one, since an Active session past its own deadline means the device never got to act. Do not add a scheduled job that ends overdue sessions server-side: the tracks still on the device would be lost, and the report would be wrong. client sessionStartTime is now stamped BEFORE the reference upload (matching the server's started_at within upload latency), so the two "Ends" clocks agree.
